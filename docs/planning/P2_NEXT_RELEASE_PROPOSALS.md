## P2-1 句向量升级（替代 BERT 的实质升级）

### 基线与口径纪律（先解决「数字不可比」）

计划给出的两个数字**口径不同，不能直接比**：

| 数字 | 口径 | 可比性 |
|---|---|---|
| bilingual F1 **0.586** | groupwise CV（按被试分组切分） | ⚠️ 见下方「溯源失败」 |
| BERT **0.536** | 组内 CV（同一被试样本可能落在训练与测试两侧） | ❌ **系统性高估**，不能与上行比 |

> **溯源状态：已解决（2026-10-05 更新）**。上一版我写「0.586 无法溯源」，该结论**已过时**：
> 基线已入库 `docs/planning/backend_text_bilingual_v2_metrics.json`（提交 `04b1e52`），
> 其中 `groupwise_ooF.f1 = 0.5864`（n=8,379、正例率 0.2163、阈值 0.3）。
>
> 同一份 metrics 还给出了**泄漏口径的量化实证**：
>
> | 口径 | F1 |
> |---|---|
> | `groupwise_ooF`（按组，防泄漏） | **0.5864** |
> | `textwise_ooF`（组内/随机划分） | **0.9964** |
>
> 同一批数据、同一模型，划分方式不同就差 **0.41** —— 任何"换个划分再看"的冲动都该先想这个数字。
>
> ⚠️ **但仍然不能直接与 2026-10-04 的 A/B 结果并列**：生产用**固定阈值 0.3**
> （按 Recall≥0.75 且 Specificity≥0.65 约束下 F1 最高者），而 10-04 的评估用
> 「每折在训练折内选最佳 F1 阈值」——后者在分布漂移的折上会把阈值推向极端并全判负。
> 两套数字口径不同，**必须用固定阈值重测才可比**（已在做，见 `P2_1_EVALUATION_RESULT.md`）。

### 评估设计（同口径 A/B，只换特征）

| 变量 | 固定为 |
|---|---|
| 语料 | `data/external/chinese_depression_corpus_v1.csv`（8,379 行，含 `source_idx`） |
| 标签 | `phq9_binary` |
| 分组 | 复用 `m2_group_cv_eval.build_group_ids`（原始样本与其增强变体同组，防泄露） |
| 分类器 | `LogisticRegression(C=1.0, class_weight="balanced", max_iter=3000, random_state=42)` |
| CV | `GroupKFold(n_splits=5)`，阈值在**训练折内**按最佳 F1 选（复用 `t1_group_cv_tool.evaluate_group_cv`） |
| **唯一变量** | 特征：A = TF-IDF(1-2gram, sublinear_tf, scale=False) ／ B = MiniLM 384 维 (scale=True) |

脚本：`scripts/t1_sentence_embedding_eval.py`（结果写入 `docs/planning/p2_1_sentence_embedding_eval.json`）。

### 候选与依赖边界

| 项 | 内容 |
|---|---|
| 候选模型 | `paraphrase-multilingual-MiniLM-L12-v2`（384 维，多语，支持 CPU） |
| 换法 | **只换特征、不换分类器**：冻结 embeddings → 接现有 LR 头 → 与 TF-IDF 特征做同口径对比 |
| 依赖边界 | `sentence-transformers` 会连带 `transformers`。生产镜像**不引入**（见 `MODEL_REGISTRY.md` §6）；若评估达标要上线，走 **ONNX 导出 + onnxruntime**，把 transformers 留在离线侧 |
| 权重体积 | fp32 约 470MB / int8 约 120MB（须与现有 26KB 占位、BERT ONNX 97.75MB 记录对照，见 `MODEL_REGISTRY.md` §3） |

### 判定门槛（涨点才换，四条全过才换）

1. **同口径 groupwise CV 下 F1 提升 ≥ +0.02**（相对 0.586 基线 → ≥ 0.606）；
2. **泄漏检查通过**：group 划分无交叉（用 `MODEL_REGISTRY.md` 记录的口径复现流程核对）；
3. **推理代价可接受**：CPU 延迟与内存相对现有 TF-IDF+LR 的倍数须在部署预算内（生产为 CPU 推理，无 GPU）；
4. **回滚方案明确**：新特征可一键切回 TF-IDF 产物（沿用现有模型版本开关机制）。

任一条不满足 → **不换**，把评估报告存档即可。**不许用「差不多」换「更好」**。

### 结论（2026-10-05 修正）：**不换**

用**生产同款配置**（固定阈值 0.3 + `zh_bilingual_tokenize` jieba 分词）重测后：

| 组 | F1 | AUC |
|---|---|---|
| TF-IDF + jieba（D，生产同款，复现基线） | **0.5709** | **0.8420** |
| MiniLM 句向量（B） | 0.5075 | 0.7568 |
| 生产基线（入库 metrics） | **0.5864** | **0.8437** |

**ΔF1 = −0.0634、ΔAUC = −0.0852 → 不换。** 详情与「为什么 10-04 会得出相反结论」
见 `P2_1_EVALUATION_RESULT.md` §1.2。

句向量路线**不否定，只否定这一个模型**：若要再试，候选改 `BAAI/bge-m3` /
`intfloat/multilingual-e5-*`，**门槛重设为超过生产基线 0.5864**，且必须用 D 组口径测。

### 本轮执行结果（2026-10-04 已完成，联网后；结论已于 10-05 修正）

**结果报告：[`P2_1_EVALUATION_RESULT.md`](P2_1_EVALUATION_RESULT.md)**（原始数据 `p2_1_sentence_embedding_eval.json`）

| 组 | 特征 | 维度 | F1 | AUC |
|---|---|---|---|---|
| A | TF-IDF 原始 | 89,988 | 0.0544 | 0.6929 |
| C | TF-IDF + SVD（**公平基线**） | 300 | 0.2452 | 0.5604 |
| **B** | **MiniLM 句向量** | 384 | **0.4692** | **0.7568** |

- **ΔF1 (B−C) = +0.2240、ΔAUC (B−C) = +0.1963，CI 不重叠 → 达到预设门槛（ΔF1 ≥ +0.02）**
- 关键证据：同为 300/384 维量级的 C 组 AUC 仅 0.5604 → **B 的增益来自语义表征本身**，不是「维度低」或「概率校准」
- **判定：换 —— 但只到「进入下一轮正式评估」这一档**：绝对 F1 0.469 仍低于项目自设目标 0.65，且仅在中文语料验证；投产前须补双语复测、补齐 F1、核算成本（470MB 权重 vs 现有 1.3MB）、修评估器（`SEEDS` 冗余循环 + 训练折阈值策略）
- 环境备忘：本机 PyPI/HF 直连不通，走腾讯云镜像 + `hf-mirror`；模型下载用 `scripts/fetch_hf_model_via_mirror.sh`（大文件断点续传）；`sentence-transformers 6.1.0` 在 transformers 5.5.0 下不可用（AutoProcessor），脚本改手工 mean pooling

## P2-2 LLM-as-judge 第二意见（可选实验）

### 现状（2026-10-04 核查后修正）

> ⚠️ **本节初版写「四处 `low_confidence` 判定应收敛到一处」，不准确**。逐处读代码后的真实结构是
> **一条链 + 一处分档**，不是四处重复判定：

| 位置 | 实际角色 | 阈值 |
|---|---|---|
| `app/ml/fusion_priority_engine.py:76` | **唯一的生产判定**：低置信 **且** 高风险 → 触发人工复核 | `conf < 0.5 and risk_level >= 3` |
| `app/core/model_engine/fusion.py:145-151` | 模态质量**分档**（primary/secondary/low_confidence），非复核触发 | `0.8` / `0.5` |
| `app/core/review_reasons.py:13` | 枚举常量定义（`LOW_CONFIDENCE_HIGH_RISK`） | — |
| `app/services/risk_service_report.py:192` | 字符串前缀消费（把 trigger 翻成报告 feature） | — |

| 项 | 实测 |
|---|---|
| LLM 客户端 | **零**（全仓唯一 `OpenAI` 字样是 `log_sanitizer.py` 的日志脱敏正则，非 SDK 调用） |
| 网关 / 密钥管理 | 无 |
| 人工金标准评估集 | 无（**只能由真人标注产生**，见下） |

### 首要门槛：合规（不是技术问题）

本系统的输入是**心理健康量表与访谈文本**。把原文发给外部 LLM 服务 =
敏感个人信息出境，可能触及 GDPR/PIPL 下的处理者义务与告知同意。
**这一条不过，技术评估无意义。** 三条可选路径（按风险从低到高）：

1. 只传**脱敏后的结构化特征**（量表分数、聚合统计），不传自由文本 —— 风险最低，收益也最受限；
2. 用**本地部署**的小模型复核（离线环境，无数据外流）；
3. 若前两条都不成立 —— **不做**。

### 本轮已完成（不花钱的部分）

1. **口径收敛**：新增 `app/core/confidence.py` 作为阈值唯一事实源——
   迁移 `fusion_priority_engine` 与 `model_engine/fusion` 的硬编码阈值，**行为等价**
   （全边界点对照 oracle 验证），并用 `tests/unit/test_confidence_thresholds.py`
   （**77 项，含把旧内联实现写成 oracle 的回归防护**）锁死口径。
   另预留 `LLM_REVIEW_ZONE = (0.3, 0.6)` 与 `in_llm_review_zone()`，
   **当前无生产调用方**（启用前必须先定合规路径）。
2. **评估集模板**：`scripts/build_llm_judge_eval_set.py` → `docs/planning/llm_judge_eval_template.csv`
   （100 条，正负各 50，按 `source_idx` 去重防泄露，长度分层），附**标注指引**。
   脚本**不生成金标准**——用规则或现有模型「生成」金标准会把待验证的判断当成基准，
   `human_label` 列必须由真人填（拿不准留空比错标更有价值）。

### 合规路径：**已选定「只传脱敏后的结构化特征」**（2026-10-04 用户决策）

即：**自由文本一律不出境**。送给 LLM 的只有结构化字段（量表分数、风险等级、置信度、
模态可用性等聚合量），`text` 原文**不传输**。代价是收益受限（LLM 看不到表述细节），
但合规风险最低，且这是唯一不需要再走数据出境评估的路径。

由此产生的设计约束（必须遵守）：
1. 评估集里 `text_excerpt` 列**只给标注者看，不发给 LLM**；
2. LLM 复核的 prompt 只能用结构化字段 —— 若实验证明「只有结构化字段」达不到 kappa 门槛，
   结论应当是**不做**，而不是放宽到传原文；
3. 任何"本地小模型"方案（原路径 2）作为备选保留：它不传数据给外部，同样合规。

### 金标准：项目语料自带**临床量表标注**（无需重新人工标注）

上一版写「人工金标准评估集：无」，据此再查一遍——**语料本身就有标注**：

| 字段 | 含义 | 是否可作金标准 |
|---|---|---|
| `phq9_score` / `phq9_level` / `phq9_binary` | PHQ-9 抑郁量表（临床标准工具）得分与分级 | ✅ **是**：量表实测，非模型输出 |
| `gad7_score` / `gad7_level` / `gad7_binary` | GAD-7 焦虑量表 | ✅ 可作焦虑维度的第二金标准 |

即：**「找经过标注的数据」在仓库里就有**——`data/external/chinese_depression_corpus_v1.csv`
自带 PHQ-9/GAD-7 临床量表标签，比事后找人标注更硬。

需要同时记住的限定：**量表是自评分数，文本是访谈转录**，两者天然会有偏差——
这个偏差正是 LLM 第二意见要处理的对象，所以它既是金标准，也不是"无误差的绝对真值"。

若仍需"AI 模拟有心理/临床背景的标注者"（用户备选方案），注意它的性质是**模拟**而非
临床判断，只能用于早期可行性探路，不能替代量表标签作为最终金标准（否则就是拿
模型判断去验证模型判断）。

### 成本预算（推荐值，含可复核的计算）

单价假设（国内主流 LLM 常见档，需按实际供应商核对）：输入 ¥2 / 百万 tokens、输出 ¥8 / 百万 tokens。
只传结构化特征时单次约 **300 input + 80 output tokens**：

```
单次成本 = 300 × 2/1e6 + 80 × 8/1e6 ≈ ¥0.0012
```

| 规模（假设） | 灰区次数/日 | 日成本 | 月成本 |
|---|---|---|---|
| demo / 毕业设计（日评估 100 次，灰区 15%） | 15 | ¥0.018 | **≈ ¥0.55** |
| 小规模试点（日评估 1,000 次） | 150 | ¥0.18 | ≈ ¥5.4 |
| 规模化（日评估 10,000 次） | 1,500 | ¥1.8 | ≈ ¥54 |

**推荐预算：≤ ¥50/月**，单次成本门槛 **≤ ¥0.01/次**（约为估算单次成本的 8 倍余量）。

⚠️ 流量是**假设值**（项目无真实流量数据）。若日评估超过约 5,000 次，月成本将触及 ¥50，
届时需按真实流量重算，或改为只对"高风险且低置信"的子集复核（可把灰区流量再降一个量级）。
