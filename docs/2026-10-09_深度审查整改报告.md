### 2.2 `e100011` 模型路径解析漂移

`settings.model_dir` 默认值是**相对路径** `"models"`，于是
`Path("models").parent == Path(".")`，使 `_abs_path` 里本应"显式配置优先"的候选 1
`model_dir.parent / raw` **退化成 CWD 相对路径并排在第一位**，与代码注释声明的
「CWD 相对路径垫底」完全相反 —— 也就是说 2026-09-24 那条 P0 修复**从未真正生效**。

实测对照：

| 路径 | CWD=仓库根（改前） | CWD=backend（改前） |
|---|---|---|
| `models/keras/*_best.keras` | 命中**仓库根影子目录**（2026-02 产物，未入库） | MISSING → 回退启发式 |
| `models/physiological/*` | 命中仓库根 | MISSING |

修法：相对 `model_dir` 一律以 `backend_root` 为锚；去掉末尾 CWD 兜底（影子目录唯一
入口）；缺失时明确 warning 而非静默。

**为什么不会打挂生产/CI**（逐条查证）：`backend/Dockerfile:197` 只
`COPY backend/models/ → /app/models/`；compose 挂 `./backend/models` 且
`MODEL_DIR=/app/models` 为**绝对路径**（走不到相对分支）；所有 CI workflow 都是

且 `backend/models/` 仅入库 4 个非权重文件，权重全不在 git。

### 2.3 `f7826ae` IP 脱敏合规功能完全跑不通

`mask_old_ips`（SEC-P2-008，GDPR 数据最小化）在 `PERF-2026-10-06` 批量化之后，
**每次执行都抛异常**，scheduler 定时任务每次跑都失败 → 30 天以上的 IP 永远不被掩码。

三种 ORM 写法在 SQLAlchemy 2.0.49 下逐一实测（lock 为 2.0.54、
`requirements.txt` 允许 `>=2.0.29,<2.1`，**都在允许区间，不是版本漂移**）：

| 写法 | 报错 |
|---|---|
| ORM update + `where(id==bindparam("b_id"))` | `bulk synchronize of persistent objects not supported ... additional WHERE criteria` |
| + `synchronize_session=False` | `No primary key value supplied for operation_logs.id; per-row ORM Bulk UPDATE by Primary Key requires ...` |
| + `synchronize_session="fetch"` | `'fetch' synchronization strategy is not available for 'bulk' ORM updates` |

最终方案：Core 层 `update(OperationLog.__table__)`（纯 executemany，不受 ORM bulk
语义与版本差异影响）+ **只过期本批受影响对象**。

> 最后一步是踩坑换来的：第一版只用 Core update 仍剩 3 红，报的是"值没变"，
> 一度以为更新没生效。真因是生产与测试的 session 都是 `expire_on_commit=False`
> （`app/core/database.py:54`、`tests/conftest.py:212`），Core 写不经 ORM 同步，
> commit 后会话内已加载对象不过期，后续读取拿到旧值（脏读）。

**关于过期范围（复核后收窄）**：第一版用了 `session.expire_all()`，虽然能解决脏读，
但它会把会话里**所有**已加载实体全部标记过期 —— 高并发/长事务下，后续任何访问都
触发重载，等于一次批量 UPDATE 引发全会话 N+1。现改为只过期本批：

```python
batch_ids = {int(u["b_id"]) for u in updates}
for obj in list(self.db.identity_map.values()):
    if not isinstance(obj, OperationLog):
        continue
    identity = sa_inspect(obj).identity   # 取主键，不触发懒加载
    if identity and identity[0] in batch_ids:
        self.db.expire(obj)
```

用 `sa_inspect(obj).identity` 而非 `obj.id`：直接读属性会在对象已过期时触发 IO，
在异步上下文中会抛错。定时任务若改为独立短会话 + `close()`，也可省掉这段，
但当前实现保持与既有服务层一致。

同类排查：全仓 `app/` 下 `bindparam` 仅此一处，无同类遗漏。

### 2.4 `762b93c` 敏感健康数据长期明文落盘

凭据层面原本是干净的（refreshToken 走 HttpOnly Cookie，access token 在
sessionStorage）。真正的问题在健康数据：心理自述片段（前 60 字 × 20 条）、生理记录
（心率/血压/睡眠）、风险评估分，三处明文写 localStorage，**只在登出/登录时清理** ——
而多数用户直接关浏览器而不登出。共享设备上下一位打开浏览器即可读取上一位的心理自述。

改到 sessionStorage：关标签页即清除，刷新仍保留（历史与 CSV 导出功能无损）。
连带修一处防线失效：`clearSensitiveLocalStorage` 改为**同时清两种 storage**，
否则迁移后"登出即清"这条防线等于失效。

### 2.5 `7ad1b96` 日志脱敏器破坏占位符 + 一处 PII 泄漏

生产真实翻车点：

```
logger.info("mask_old_ips: masked=%d (cutoff=%s, days=%d)", 0, ts, 30)
```

键名清单含 `ip`，正则把 `"mask_old_ips: masked"` 当成"敏感键=值"整段替换 →
占位符从 3 个变 2 个而 args 仍 3 个 → `TypeError: %d format: a real number is
required, not str`。logging 内部只在 `handleError` 打印一行，**该条日志直接丢失**。

这同时是全量回归里 `test_sec_p2_008_ip_masking` 7 条失败的根因：
`sec_p2_007` 的测试调用 `configure_logging()` 把 `SanitizingFilter` 装到 root logger
且**未还原**，污染同会话后续全部测试。

修法三步（缺一不可）：

1. 先 `record.getMessage()` 渲染 → 对文本脱敏 → `msg` 固定为字面量 + `args=None`
2. 渲染失败（参数本身不匹配）时原样放行，不把脱敏器变成故障放大器
3. **dict args 必须先按键名打码再渲染** ——
   `"cfg %(password)s" % {"password": "x"}` 渲染后键名消失，只做值级脱敏会得到
   `"cfg x"` **明文泄漏**。这一步第一版漏了，是跑既有测试报
   `non_sensitive_container_preserved` 失败才发现的。

> **已知代价**（本轮不重写，留待后续）：
> 1. **结构化 args 丢失** —— 脱敏后 `msg` 固定为字面量、`args=None`，后续若接
>    JSON formatter / ELK 解析 `record.args` 的结构化字段将失效。
> 2. **渲染失败路径会原样落盘一次** —— `getMessage()` 抛异常时按原样放行，
>    该条日志里的敏感内容不会被脱敏。
> 后续需做 token 级保护：只替换 value，不碰 `%d` / `%s` / `%(name)s` 结构。

### 2.6 `8463cf9` 脱敏按键名分层（方案 B）+ 两处测试对齐

采纳"键名命中时若值像 email/phone/IP 则保留部分掩码"。**分层规则是从既有测试反推的，
不是自拟**：

| 测试 | 固化的原设计 |
|---|---|
| `test_id_card_masked`（注释明写"id_card 作为敏感键时整体被脱敏"） | 高敏键 → 整段打码 |
| `test_id_card_standalone`（裸身份证"保留首尾"） | 裸值 → 部分掩码 |
| `test_email_preserves_first_char` / `test_phone_masked` | 低敏键 → 部分掩码 |

途中踩到并修掉一个**自引入**的 bug：第一版对所有键名都尝试部分掩码，**破坏幂等性**
—— `a***@test.com` 二次 sanitize 时 email 正则匹配不上（含 `*`），被判为"无特征值"
而整段打码。豁免收紧为「非高敏键 且 值含 `*` 视为已脱敏」；高敏键不走豁免
（`token=***JWT_MASKED***` 仍整段打码）。

另修两处**测试未跟上实现**（与本次实现无关，产品行为本身正确）：

- `TestRequirePermission` 3 条：P0-1 给 `require_permission` 的 checker 加了
  `request` 形参（租户一致性校验），测试仍按旧签名 `checker(user)` 调用 → TypeError。
  **产品行为正确的证据**：`tests/api/test_auth_p0p1.py::test_profile_update_and_change_password`
  端点级用例通过，且明确断言 `profile_data["email"] == "new_email@test.com"`（明文）——
  说明整条依赖注入链与 `profile` 端点在真实 HTTP 层工作正常；
  `tests/api/test_p0_p1_regressions.py` 亦覆盖同端点。
- `test_perf_p2_009` 2 条：PERF-2 给 `_model_fingerprint()` 加了 10s TTL 记忆化，
  测试连续调用时命中上一例的缓存（拿到旧指纹 / 两次键相同）。第二次调用前还需
  再复位一次（第一次已把结果写回缓存）。**产品行为正确的证据**：同类的
  `test_cache_key_contains_fingerprint`（断言缓存键必含指纹）、
  `test_fingerprint_is_deterministic`、`test_fingerprint_handles_unreadable_paths`
  均通过——指纹机制本身没问题，只有这两条用例自身未考虑记忆化。

## 4. 归因方法论（可复用）

本轮 24 条失败的定位过程值得固化：

1. **单独跑失败文件** → 绿则不是自身逻辑问题（`ip_masking` 单独跑 23 passed）
2. **按字母序看清单** → 全排在目标文件之前 ⇒ 怀疑前序测试污染全局
3. **逐个前置文件与目标文件同跑** → 锁定污染源（`test_sec_p2_007`）
4. `--tb=line` 输出落盘再 grep，读真正异常

两条纪律：

- **不要用 `grep ... | head -N` 核验失败清单** —— 我曾因此漏看 FAILED 行、
  误报"某文件已通过"（`test_perf_p2_009` 被误判为绿）
- **不要在跑全量时并发跑其它 backend 测试** —— 共用 `test_app.db`，
  会报 `database is locked`（fixture setup 阶段）制造假红

### 5.1 schemathesis 契约 flaky：IDN 邮箱双校验器冲突

失败节点 `test_api_contract[PUT /api/v1/auth/profile]`，**已拿到确凿证据**
（schemathesis 自带可复现命令）：

```
请求:  {"email": "h@fcqr6axccp.liti0ydoe2-dg.xn--3bst00m"}   ← punycode
响应:  {"email":"h@fcqr6axccp.liti0ydoe2-dg.集团"}            ← 规范化成 unicode IDN
→ Response violates schema (ProfileResponse)
```

Pydantic `EmailStr` 接受 punycode 并规范化成 unicode；jsonschema 的 `format: email`
基于 RFC 5322、不接受 unicode 域名 → 判不合规。只有 hypothesis 恰好生成 punycode
域名时触发 ⇒ 低频 flaky（前两轮全量清单里都没有它）。

**定性**：Punycode → Unicode 是 Pydantic 的**标准规范化行为**；错的是
`format: email` 的 jsonschema 校验器不支持 unicode 域名。这是**校验器之间的能力
差异**，不是本项目的 bug。

**处置（定夺）：选 B —— 短期接受 flaky 并记录在案。**

> ❌ **方案 A 不推荐：为让测试变绿而在请求侧禁用 IDN（让请求返回 422）**
> 这等于**为了测试收窄产品功能** —— 此前系统接受的 IDN 邮箱会被凭空拒绝，
> 而 IDN 邮箱本身是合法邮箱。工具适配性问题不应转嫁给用户。

**长期 ticket**（二选一，尚未实施）：

1. `ProfileResponse.email` 统一序列化为 punycode ASCII 输出（与请求侧规范化对齐，
   也便于下游存储/比对）
2. 或对该端点放宽 schemathesis 的 format 检查（需先确认 schemathesis 是否支持
   按端点覆盖格式校验策略）

**复现方式（证据已入库）**

探针：`backend/tests/contract/probe_contract_profile_idn.py`（2026-10-09 入库）。
文件名不匹配 `test_*.py`，**不会被 `pytest tests/contract/` 自动收集**，需显式运行：

```bash
cd backend
.venv/Scripts/python.exe -m pytest tests/contract/probe_contract_profile_idn.py -q
# 实测：max_examples=200 约 16 秒复现；max_examples=10 不复现
```

> `tests/conftest.py` 的环境初始化（建表 + 测试库 `test_app.db`），无法在合理
> 时间内跑完（300s 超时）。**证据脚本跑不动就等于没有证据**，故就近入库。
